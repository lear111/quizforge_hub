# QuizForge 双仓库开发与发布流程

## 当前状态

这是两个仓库的维护约定与待落实的 GitHub 配置方案。Web 已有贡献指南与 PR 模板；Hub 本次补充贡献指南、PR 模板和 CODEOWNERS。文件写入工作区不等于提交、推送或启用远程规则。两个仓库的本地工作区仍有未提交改动；现有云端快照包含工作区内容，不能仅凭当前 Web HEAD 还原线上版本。

下一步先整理可发布的源码基线，再加入 Web 版本锁定文件和自动检查。CI 成功运行并确认检查名称后，才能在 GitHub 设为必需检查。尚未落地的自动检查不得写成已启用。

## 仓库职责

| 仓库 | 内容 | 更新方式 |
| --- | --- | --- |
| quizforge_web | 共享刷题核心、页面、题型协议、官方基础内容、本地启动与安装 | 修改源码并测试，从已提交的版本构建 |
| quizforge_hub | 账户、广场、私人数据隔离、配额、云端适配和部署 | 修改云端代码，或通过独立 PR 升级锁定的 Web 提交 |

共享缺陷在 Web 修复；Hub 可以先做有说明、有回归检查的临时适配，但需关联上游 Issue，并在升级后核对是否移除。不要长期手工维护两份分叉的刷题核心。

## 云端功能基线

云端以所锁定 Web 版本的完整用户功能为基线，叠加账户隔离、配额和明确约定的限制。默认保留题库与分组管理、题目编辑、作答、白板、历史及考试等功能；不能因复用本机权限开关而一并关闭用户管理自己内容的能力。

- 已明确移除的本机网络连接设置、拓展开发与管理入口按云端产品约定处理；未知拓展执行继续受审核约束。
- 登录、存储隔离、配额或浏览器直连 AI 需要改造实现，但应保持已约定的用户能力。功能未接通时记录为未完成，不能追认为产品限制。
- 新增云端限制必须在 PR 中逐项列明功能、依据和影响；未明确约定的本地功能消失，按回归问题处理。
- 功能对齐需按 Web 功能清单及云端差异逐项验证。核心代码已复制、自动测试通过、服务已部署，都不能单独证明完整功能已经对齐。

## 每次改动

流程：明确问题 → 从干净主线创建短期分支 → 修改和验证 → 推送分支 → PR → 审查与自动检查 → Squash 合并。

- 小修复可直接提 PR；较大功能、重构、接口和数据迁移先讨论 Issue。
- 分支使用 `feat/说明`、`fix/说明`、`docs/说明`、`chore/说明`，例如 `fix/cloud-ai-retry`。
- 一个 PR 对应一个可以独立解释、验证和回退的问题，PR 内可有多个提交。
- 多人或多个 AI 会话同时修改同一仓库时，使用各自的分支与独立工作区，避免混入其他人的未完成改动。
- 不在已有混合改动的工作区直接运行整仓库暂存或打包发布。先逐项检查归属和公开范围。

提交信息采用简短的 `类型(范围): 改动`，中文或英文均可，例如：

```text
fix(ai): 避免重试时重复调用模型
feat(account): 展示每日下载额度
docs(contributing): 说明云端测试准备方式
chore(runtime): 升级已验收的 Web 核心版本
```

PR 标题概括最终行为；描述包含问题与结果、影响范围、兼容性、测试命令及结果、页面验证和未覆盖项。关联 Issue，但 Issue 对小修复不是额外门槛。

## 外部贡献与审查

| 参与者 | 提交方式 | 合并与发布 |
| --- | --- | --- |
| 外部贡献者 | Fork → 分支 → 上游 PR | 由维护者审查、合并 |
| 受信任协作者 | 仓库内分支 → PR | 按维护者分工审查 |
| 项目负责人 | 分支 → PR → 检查通过 | 可自行合并自己的 PR；发布另行执行 |
| AI 助手 | 在授权范围内修改、验证；获准提 PR 时完成提交和 PR | 提 PR、合并、发布和部署分别遵循当前任务授权 |

GitHub 初期强制 PR、必需测试和解决审查讨论；外部 PR 由负责人审查合并。只有一位维护者时，暂不强制所有 PR 都获得另一人的批准，以免负责人自己的 PR 无法合并。新增第二位稳定维护者后，再启用至少一名非作者的审批要求，并按模块调整 CODEOWNERS。

CODEOWNERS 用于明确审查责任和请求审查，不自动授予写权限；强制代码所有者批准需要另外配置 GitHub 规则。涉及登录、用户隔离、文件路径、配额、凭据、数据迁移和发布工作流的改动要重点审查。

## GitHub 配置目标

两个仓库对 `main` 设置：

- 必须通过 PR 合并。
- 已确认的必需 CI 检查必须通过；检查名保持稳定，不使用会因路径过滤而一直挂起的必需工作流。
- 审查讨论解决后才能合并。
- 禁止强制推送和删除主分支。
- 默认使用 Squash 合并，并清理已合并的短期分支。

贡献者 CI 使用 `pull_request`、只读权限和 GitHub 托管运行器，不读取生产凭据。发布或部署使用维护者控制的工作流，不在运行外部 PR 代码的任务中发放服务器权限。

计划中的 CI：Web 检查共享核心与本地构建；Hub 按锁定提交检出 Web、生成运行快照、运行全部云端检查。涉及云端核心的 PR 不能依靠“未准备快照所以跳过”取得通过结论。

## 核心同步与版本发布

Hub 的 Web 版本锁定文件应记录仓库、完整提交 SHA 和可读版本标签。构建时检出该提交；工作区改动不作为可发布版本输入。运行快照记录文件哈希，部署包记录 Hub 提交、Web 提交和包摘要。

更新共享核心：Web PR 合并 → 选定已验收提交 → Hub 提出版本锁定升级 PR → 云端检查与页面验收 → 发布云端包。本地和 Hub 使用各自的版本标签与 Release；版本号无需强行一致，但都能追溯到共享核心提交。

只有 Hub 适配变化时，可以单独发布 Hub，沿用原 Web 核心版本。

合并 `main` 表示进入主线，不等于已经上线。发布由维护者从确定的提交生成包，保存校验值和发布说明；云端部署先备份并验证恢复路径，再切换发布目录和检查服务。业务数据不进入 Git 或公开发布附件。

## 现有未提交改动的处理

Web 与 Hub 分别盘点，按实际依赖划分可审查的提交和 PR；互相依赖的目录迁移、格式变化及相应测试保持在同一可运行单元中。不得为了机械缩小 PR 而拆成不能运行的主线提交，也不得把不同会话的全部工作一次暂存。

先核对必要构建文件、自动检查、许可证与文档均进入对应仓库，再选定 Web 提交并构建可复现快照。现有部署继续按已保存的发布包追溯，不能追认它等同于一个不含这些工作区改动的 Git 提交。
