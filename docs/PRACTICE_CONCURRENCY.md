# 练习空间的用户并发

本轮修复仅修改 Hub 的 Node 练习适配层，不改 Web 固定快照、题库格式、拓展接口或 Java AI 计费逻辑。源码修复不表示测试站或正式站已经更新。

## 问题与修复

旧 `CloudPractice.serial(operation)` 的单个 Promise 链包住了全站所有练习 API，包括读取、保存、AI 任务认领和评分结果保存。一个用户等待规则执行或磁盘操作时，其他用户也在同一队列等待；全站队列原上限为 16。模型生成本身不在这个队列里，不能把这次问题描述为所有模型请求只允许一个执行。

现在按已认证的用户 ID 分队列。同一用户的所有工作区、旧导入别名、合并、导入、导出和删除仍按顺序执行，防止它们访问相同物理目录时交错；不同用户的异步操作可以并发。用户队列最多 16 个待完成操作，全站最多 128 个待完成操作、32 个有请求的用户队列。失败不阻塞后续操作，完成后删除队列，关闭服务时等待所有已接纳的操作结束。

会话缓存从 2 个调整为最多 32 个。满额时只回收空闲会话，不关闭正在执行请求的会话；全部繁忙时返回 503，不建立无限会话。会话建立和回收使用独立生命周期屏障，已有可用会话不经过该屏障。用户在回收期间重新访问时，会等旧实例关闭、文件锁释放后再建立新实例。上传占用标记也按账号隔离。

每个用户的检查点、恢复目录、配额和答案所有权检查仍保留。数据库事务不跨异步等待；失败只回滚该账号的工作区。规则执行仍受审核和独立运行器的资源限制。

## AI 网关的区别

Java 网关原本就允许并发；保留 `AI_SITE_CONCURRENCY`（默认 2，范围 1–8）以及同一账号最多 2 个调用。超过网关并发容量立即返回 429，不在练习全站队列里长时间等待。本轮不擅自提高模型供应商的并发预算，也不取消限流。

新增 Java HTTP 测试让两个不同练习账号同时进入受控模型调用，在任一个调用完成前确认两者均已开始，并验证查询余额不被模型等待阻塞、扣费分别记在自己的账号。使用合成模型，无真实费用。

## 验证与发布边界

`test/practice-concurrency.test.mjs` 验证 30 个用户队列独立推进、同账号顺序、过载与失败恢复、停服等待；真实本机 HTTP 验证一人暂停时另一人仍能读取和保存、缓存回收与重新访问、跨账号拒绝，以及一人回滚不影响另一人的已保存答案。

同时回归 AI 的任务认领、重复结果、人工评分覆盖保护、考试、历史、工作区管理和网络听力。执行记录见本轮开发日志及 `.temp/practice-concurrency-regression.tap`、`.temp/practice-ai-concurrency-java.log`。

这些检查证明调度和账号隔离，不等于完成 30 人真实题库、真实模型、磁盘负载或手机操作的容量验收。同步文件扫描、检查点复制和新用户默认题库准备仍可能占用事件循环；首次建立会话仍需生命周期管理，本轮没有取消这些安全步骤。

上轮 `.temp/web-sync-20261027-network/release-final` 是修复前的候选，不能直接作为含此修复的发布包。发布前应重新生成练习服务源清单和运行包，在测试站验证后再按独立发布流程切换正式服务；保留用户数据和回退版本。

复现对照：诊断预加载脚本仅在测试进程中恢复旧的全站队列（适配新方法签名，忽略用户 ID），同一 HTTP 用例在 `warm Bob API` 等待断言失败；恢复修复代码后通过。日志为 `.temp/practice-concurrency-before.tap` 和 `.temp/practice-concurrency-final.tap`。这不是对线上用户施加阻塞，也不是线上性能压测。

修复阶段结果：Node 相关 5 个测试文件共 19/19 通过（0 失败、0 跳过）；最终并发文件另行复测 3/3，通过项与前者重叠。Java AiHttpTest 共 8/8 通过，包括新增跨账号模型并发及扣费检查。源码及日志 SHA-256 见 `.temp/practice-concurrency-validation.json`。该阶段只改源码；随后用户授权正式发布，已于2026-10-27上线，重新执行的全量检查和发布证据见[正式发布记录](../deploy/production-20261027.md)。
